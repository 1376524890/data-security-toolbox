## 一、漏洞库永久停在 `Error: 任务不存在`

**现象**：漏洞库页面顶部一直挂着 `Error: 任务不存在`，刷新、退出登录再进都不消失；「更新漏洞库」
「导入 Grype DB」按钮点不动（`busy` 被卡住）。

**根因**：两侧各自都对，是**生命周期错配**。

- 客户端把 Grype 任务的 id 记在浏览器 `localStorage['grype-library-job']`，**跨会话、跨部署存活**；
- 服务端把任务状态写成 `settings.storage_dir/library_jobs/<id>.json`，而 `storage_dir` 是
  `deploy-data` 下的 bind mount，**重新部署就换了一份**；
- 于是页面拿着一个**新容器从没听说过的 id** 去轮询 `GET /offline/grype/jobs/{id}`，
  `api/integrations.py::job_path` 找不到文件 → `404 任务不存在`；
- `useVulnerabilityLibrary.poll()` 把 404 当成普通错误写进 `error`，**然后照旧每 2 秒排下一次轮询**：
  报错清不掉，轮询也永远停不下来。本机 `deploy-data` 被换过多次，这个 id 因此长期存活。

**修复**：

- `frontend/src/api/client.ts`：响应拦截器把 HTTP 状态码挂到 Error 上（`failure.status`）。
  此前调用方只有一句中文，分不出「这条记录没有了」（404）和「服务端不健康」（5xx），
  而这两者的处置完全相反。
- `frontend/src/modules/collection/composables/useVulnerabilityLibrary.ts`：`poll()` 认 404 为
  「任务已不存在」——清 `localStorage`、复位 `busy`、`job` 置空、`hint` + 一次 warning 说明
  「上次的漏洞库任务已不存在（重新部署后任务状态不会保留），已清除本地记录」，然后 **return
  （不再排下一次）**。非 404 的失败仍旧重试并记入 `error`（瞬时故障不该终止展示）。
- **判别依据是状态码，不是文案**：服务端换措辞不会让这段逻辑失效。

**回归**：`frontend/src/__tests__/cve-network-state.test.ts` 新增 2 项（404 → 清记录 + 停表 +
只提示一次；502 → 保持等待 + 保留 id + 记入 `error`）。

## 二、pcap 抓包段刷屏任务监控

**现象**：任务中心默认列表被一条条 `pcap` 行占满（本机 `GET /tasks` 共 94 行，最新 8 行全是 `pcap`），
真正的监控任务、扫描任务被挤下去。

**根因**：`services/probe_task_service.py::default_task_filter()` 隐藏抓包段时**完全押在
`payload['monitor_task_id'] IS NULL`** 这一个字段上，而段与监控任务的**挂链只发生在上传那一刻**
（`api/pcaps.py` 调用 `monitoring.ensure_monitor_task` + `attach_segment`）。因此两类行会留下没有链接的段：

- 上传时探针**没有 Running 监控任务**（挂链拿不到 monitor）；
- 挂链机制存在**之前**就已建好的行。

这些行满足 `monitor_task_id IS NULL`，于是以裸 `pcap` 行身份进入默认列表。本机库里 `pcap` 共 1685 行，
其中 **76 行没有链接**，正好就是刷屏的那批。

**修复**：默认列表**直接排除 `kind='pcap'`**（用 `monitoring.SEGMENT_KIND`，不写字符串字面量），
再叠加原来那条链接条件。段的可达性不变：`kind=pcap`（任务中心的类型下拉里本来就有）仍能翻到全部段。

**实测**（本机重启后端容器后）：`GET /tasks` 总数 **94 → 18**、无 `pcap` 行；
`kind=pcap` 仍返回 1261 段；驾驶舱「最近任务」（与任务中心共用同一个过滤器）只显示
monitoring / scan / file_source_scan。**过滤即修复，没有改一行历史数据**——76 行历史段原地保留。

**回归**：`backend/tests/test_monitoring_stop.py` 新增 1 项（没有链接的段不出现在默认列表里，
但仍能按 `kind=pcap` 找到）。

## 三、大屏两张图分开切换，并在地图上画出数据流动链路

**现象**：数据大屏中心列把「数据流动」和「地理位置态势」上下并列，各占一半高度——一张地图矮到
看不清自己的连线；而且地图上看不出数据从哪儿流到哪儿。

**修复**：

- 中心列改成**两个可切换的视图**：`数据流动`（默认）/ `地理位置态势`，同一时刻**只渲染一张图**，
  当前图拿满整列高度。切换状态 `centerView` 与既有的 `metric` 一样放在
  `composables/useDashboardScreen.ts`，视图不再自己持有状态。
- `components/GeoMap.vue` **在地图上画出数据流动链路**：从内网 hub 到每个目的国家/地区一条曲线，
  **粗细 = 数据量、颜色 = 该组敏感等级**，虚线沿 hub → 目的地流动（方向是静态线说不出来的），
  悬停给出「内网 → 美国 · 2 主机 · 4.0 KB · L3 高敏感个人信息」。
- 链路按**目的地区分组**绘制，**不画主机到主机**：`GET /dashboard/geo-map` 只把目的地址判定到国家、
  没有主机级坐标，画主机连线等于声称一个没人测量过的几何。内网本身也没有地理坐标（RFC1918），
  所以它是**一个示意 hub**（中国图上画在开阔海面，地球上画在圆心），标签写明「示意」。
- **地球改为朝向数据量最大的境外目的地**：地球只能朝一面，原先固定 105°E，`-98.6°` 的美国
  落在背面被 `filter(visible)` **静默丢弃**。现在按最大流量目的地定朝向，背面剩下的组在脚注里
  计数（「地球背面 N 组未绘制」），不再无声消失。

**回归**：`frontend/src/__tests__/dashboard-screen.test.ts` 新增「切换中心列」1 项（两个 tab、
一次只渲染一张图、切回、链路数与标题、背面无遗漏）；`dashboard-screen-state.test.ts` 新增 1 项
（`centerView` 默认 `traffic`）。
