## 一、四项需求

实现细节见 `CHANGELOG.md` 同日条目与 `PROJECT_STATUS.md` 第五十批，此处只记交付口径。

**① 自动刷新**：`frontend/src/composables/useAutoRefresh.ts` 统一三条保证——上一拍没回来不再排下一拍、
`document.hidden` 时不轮询、卸载清 timer；刷新一律 `load({ silent: true })`，后台失败保留上一次
成功的数据。间隔：任务中心 15 s，抓包工作台/看板/文件/资产/流量 30–60 s，规则库/漏洞库 120 s；
`LoginView` 与编辑中的表单不轮询。

**② 筛选 + 点击列标题排序**：后端新增 `backend/app/api/list_sort.py`，`order_by=field` / `-field`
走白名单，**未知列直接 400**；已接入 `/tasks`、`/files`、`/pcaps`、`/data/assets`、
`/network/assets`、`/asset-instances`（并新增 `severity` 过滤）、`/offline/cves`（并新增
`severity`/`source` 过滤）。一次取全的列表在浏览器内筛选排序。前端 `useTableSort` 换顺序时
**同时把页码复位到第 1 页**。

**③ OCR 红头 / 涉密判定**：`shared/scanning/ocr.py`（tesseract `chi_sim+eng`、`pdftoppm` 150 dpi）
+ `shared/scanning/document_types.py`，产出 `DATA_CLASSIFIED_001`（绝密/机密 Critical、
秘密/通用 High）与 `DATA_REDHEAD_001`（Medium）。覆盖面接入 `engine/data_engine` 与
`services/file_scan/ingest.py`。**探针不做 OCR**：探针分发包里没有 tesseract，
`shared/scanning/ocr.py` 无工具链时如实报 `unavailable`（「未检查」），不装成「干净」。

**④ 更名**：用户可见名称统一为「数据安全监测检测工具箱」；**刻意不动** systemd 单元名
`data-security-toolbox-probe` 与 `/opt|/etc|/var/lib/data-security-toolbox`——改这些等于让已下发的
探针失联。

**⑤ 密码评估按资产常驻**：`useCryptoAssessmentResults.ts` 把含密码评估的检查任务**折叠成一行一台
主机**（同一主机取最新一次观测），行里直接带 `level`/`overallScore`/`violations`；检查任务表降级为
观测来源。判定口径共用 `configFromProfile()` + `assessCrypto()` 一份实现。**无后端改动、无迁移**。

## 二、测试结果

| 面 | 结果 |
| --- | --- |
| 前端 | **23 文件 / 147 项通过**（新增 `auto-refresh-table-sort.test.ts` 15 项、`rule-versions-state.test.ts` +4、`crypto-assessment-results-state.test.ts` +6） |

**跑后端全量必须带 `SECRET_KEY`**：`core/config.py` 的凭据加解密要求

按仓库既有跑法（`docker compose run` 会带 `.env`）或显式 `SECRET_KEY=... python -m pytest`，
失败数从 40 降到 11。

镜像包与代码必须成套升级：`backend/Dockerfile` 的 base 阶段新增 tesseract/poppler，
`docker load` 的镜像包里必须包含它们，否则 OCR 全部 `unavailable`。

## 三、真机验证

### 3.1 本机 192.168.110.168（arm64 桌面）

新镜像替换本地旧栈后 `--force-recreate` 起 8 个服务，全部 `healthy`；
`/openapi.json` → `3.3.0`、`info.title` 为「数据安全监测检测工具箱」，控制台标题同步；
`source-backend-1` 内 `tesseract --list-langs` 列出 `chi_sim` / `eng`。

前端下发**探针任务**（`POST /probe-deployments`，SSH root，profile standard）：
preflight 8 项全 PASS，状态 `PREFLIGHT → INSTALLING → ONLINE`，探针 `online`、`agent_version 3.7.0`。
随后下发**检查任务**：`POST /scan`（带 `probe_id`）→ `Success`；`POST /probe-deployments` 配置的
`data_paths` 采集任务 → `Success`（44 文件 / 89 检测）。

OCR 用**真实样本**端到端复核（生成带噪点、轻微旋转的图片与无文本层 PDF，在发布镜像内跑
`DataEngine().analyze()`）：

| 样本 | OCR | `document_type` | 敏感度 | 规则 |
| --- | --- | --- | --- | --- |
| 红头通知（PNG，扫描质感） | complete | 公文 | Low | `DATA_REDHEAD_001` Medium |
| 涉密报告（PNG，`机密★5年`） | complete | 涉密文件 | **High** | `DATA_CLASSIFIED_001` High |
| 红头通知（**图片型 PDF**，走 `pdftoppm`） | complete | 红头文件（公文） | Low | `DATA_REDHEAD_001` Medium |
| 普通表格（PNG，对照） | complete | 空 | Low | 无 |

对照样本不出结论，说明判定不是「凡是图片都报」。

**本机一处环境限制（非缺陷）**：`/home` 已用 92%，低于存储护栏的 10% 下限，
`POST /files/upload` 被如实拒绝（「数据分区剩余 24869 MB，低于保留下限 30292 MB」）。
护栏按设计工作，因此本机未走 HTTP 上传路径验 OCR，改用引擎直跑（上表）。

### 3.2 192.168.110.50（arm64 银河麒麟）

**停机与清理**：旧栈（3.2.0，9 容器）`docker stop/rm` 后删除
`dst-toolbox-3.0.0-linux-arm64`、`dst-toolbox-3.2.0-linux-arm64`、
`dst-toolbox-3.2.0-linux-arm64.prev-20260923-192256`、`deploy-data-3.0.0-backup`、
`_stage32fix`、`build-src`，以及 `dst-toolbox-3.0.0-linux-arm64.tar.gz`、
`dst-toolbox-3.2.0-linux-arm64.tar.gz(.sha256)`、`dst-toolbox-3.2.0-linux-arm64.new.tar.gz`、
`replace32*.sh`、`replace32fix*`、`build.log`、`docker_setup.sh`；`docker image prune -f` 回收
**5.16 GB** 悬空层。根分区 `/` 由 **89% 用满（剩 11 GB）降到 29%（剩 67 GB）**。
`.50` 上 no-password sudo，特权文件操作经 `docker run -u 0 -v /home/user:/home/user` 的
helper 容器完成；随后 `chown -R 1000:1000`，整棵树归 `user`，便于操作者自行运维。

**新版本部署**：交付包 sha256 校验 `OK` → 解包到 `~/dst-toolbox-3.3.0-linux-arm64`
（`VERSION` 记 3.3.0 / 探针 3.7.0 / head 0019 / Git `9c11770`）→
`./deploy.sh --non-interactive --http-port 8080 --api-port 8000 --backend-url http://192.168.110.50:8000`。9 个容器全 `Up`，backend/worker/pcap-worker/
postgres/redis `healthy`；`/openapi.json` → `3.3.0`，「数据安全监测检测工具箱」；
`/api/v1/health` → `status: ok`，redis ok、broker ok、workers 3；控制台 `/` 200 且标题正确。

**从 .50 向 .168 下发任务**：preflight 8 项全 PASS →
探针任务 `PREFLIGHT → INSTALLING → ONLINE`、探针 1 号 `online`；随后
**检查任务**（探针侧 `probe_scan`）`Success`，`assets 3 / hosts ['192.168.110.168'] / ports 22,80,443,8000,8080`；
**平台侧 `scan`** `Success`，`assets 3 / findings 10`，并写入
`result.crypto_profiles['192.168.110.168']`（算法 Ed25519/ECDSA/RSA、keyLengths 256/2048、
`serviceCount 3`）——`GET /tasks?kind=scan` 因此能给出**按资产的密码评估常驻结论**。
探针数据资产采集 `Success`（8 条，含 `.168` 上那批 OCR 样本）；持续监测 `monitoring` 任务
`Running`（57 段：33 analyzed / 24 进行中 / 0 failed）。

**注意**：探针安装路径与 systemd 单元名在 .168 上是**唯一**的，因此 .50 下发探针会把 .168 上
原来指向本机 8000 的探针**改为指向 .50:8000**（这是「在 .168 上下发探针任务」的必然结果）。
